# 아키텍처 개요

> 상태: **v0.7** · 2026-10-23 · 상위 기준: [`../SOT.md`](../SOT.md)
> 이 문서는 SoT의 요구사항을 어떤 구조로 구현할지 정한다. SoT와 충돌하면 SoT가 우선한다.
> Owner 결정(DB-01~04, 모두 B)을 반영한 부분은 해당 브리프 ID로 표시한다.

---

## 1. 전체 구조

브라우저 단일 앱이다. 서버, DB, Python 런타임이 없다.

```text
┌──────────────────────────── UI (React) ─────────────────────────────┐
│  Explorer   Tabs   EditorPane(Monaco)   Terminal   StatusBar        │
└──────▲───────────────────────▲─────────────────────────▲────────────┘
       │ 선택자(selectors)      │ 실행 요청(Run)            │ 로그
┌──────┴───────────────────────┴─────────────────────────┴────────────┐
│ App wiring: 상태 보관, 이벤트 연결, 자동 저장 트리거                    │
└──────▲──────────────────▲───────────────────────▲───────────────────┘
       │                  │                       │
┌──────┴──────┐  ┌────────┴────────┐   ┌──────────┴──────────┐
│ Engine      │  │ Scenario data   │   │ Persistence adapter │
│ (순수 TS)    │◀─│ (Engine 타입 사용) │   │ (localStorage)      │
└─────────────┘  └─────────────────┘   └─────────────────────┘
```

### 1.1 의존 방향

- **Engine**은 React, Monaco, localStorage를 import하지 않는 순수 TypeScript다. 입력(시나리오 + 플레이어 선택)에서 출력(상태, 로그, 파일 내용)을 결정적으로 계산한다.
- **Scenario data**는 Engine의 타입에만 의존한다. 엔진 코드를 바꾸지 않고 시나리오를 교체할 수 있어야 한다(ideation §6.2).
- **UI / Persistence**는 바깥 어댑터다. Engine 쪽으로만 의존한다.
- Monaco 전용 처리(읽기 전용 범위, 단축키, 데코레이션)는 `ui/editor/` 안에만 둔다.

## 3. 실행 흐름 (`Ctrl+Enter`)

```text
1. App(`runScene`, 순수 함수): 실행 대상 = derive 결과의 currentSceneId (해당 스테이지 파일의 마지막 함수)
   - null(엔딩 도달)이면 → Terminal 안내 한 줄, 종료
   - 활성 탭이 그 사건의 스테이지 파일이 아니면 → Terminal에 실행할 파일 안내 한 줄, 종료 (SoT §3.5)
2. App: 입력 리터럴 = 각 필드에 대해 playerEdits[scene.id][field] ?? 값 슬롯의 defaultLiteral
   Engine.parse(scene, 입력 리터럴) → 성공: Choice / 실패: ParseError[]
3. 실패 시: Terminal에 오류 출력, Progress·Explorer·파일 내용 변경 없음 (AC-07)
4. Engine.apply(scenario, progress, choice) → 새 Progress
5. Engine.derive(scenario, 새 Progress)     → 해금 파일, 파일 내용, 로그, 엔딩
6. UI 갱신 (Explorer에 새 파일, Terminal 로그). Terminal = derive의 로그 + 안내·오류 같은 일시 출력(저장하지 않으므로 새로고침하면 사라진다)
7. Persistence.save(SaveSnapshot)
```

- 3단계의 "상태 변경 없음"이 AC-07의 핵심 보증이다. 파싱·검증이 끝나기 전에는 어떤 상태도 쓰지 않는다. 바뀌는 것은 Terminal 오류 출력뿐이다.
- 실행 대상은 항상 현재 사건 하나이고, 그 사건의 파일이 활성 탭일 때만 실행한다(SoT §3.3, §3.5). 커서 위치는 상관없다. 해결된 함수는 다시 실행할 수 없다. 다른 탭에서 누르면 1단계에서 안내만 하므로, 새로 해금된 파일은 열어야만 진행된다(AC-05).
- 1단계의 두 안내 경로와 3단계 실패 경로 모두 Terminal 출력 외에는 아무 상태도 바꾸지 않는다.
- 플레이어 코드는 어떤 경로로도 실행·`eval`되지 않는다 (R-08). `main.py` 실행(§3.1)도 같다.

### 3.1 `main.py` 실행 — 시나리오 선택 (SoT v0.8 §3.7)

```text
1. 활성 탭이 main.py면 runScene 대신 runHub(순수 함수): main.py의 scenario·restart 값을 같은 parser로 검증
   - 실패 → 사건과 같은 Traceback, 아무것도 바꾸지 않음
2. 지금 시나리오를 즉시 저장 (편집 값·탭 포함)
3. choose(): restart면 고른 시나리오의 저장 삭제 → 고른 id 기록
4. App이 작업 공간(Workspace)을 새로 마운트: 고른 시나리오의 저장을 복원하고 현재 사건 파일을 연다
```

- App은 두 층이다. 바깥 `App`은 고른 시나리오만 보관하고, 안쪽 `Workspace`가 지금까지의 진행·편집·탭·저장을 맡는다. 시나리오를 바꾸면 `Workspace`를 다시 만들어 상태가 섞이지 않는다.
- `main.py`(`app/hub/`)는 시나리오가 아니라 앱 소유다. 텍스트는 템플릿 + 시나리오 목록(제목, 소개, 상태)으로 매번 만들고, 값 슬롯은 엔진의 `findValueSlots`로 찾는다. 편집 키는 `PlayerEdits`의 `hub`이며 저장하지 않는다.
- 시나리오를 고르지 않은 상태에서는 Explorer에 `main.py`만 있고, 다른 곳에서 실행하면 안내 한 줄만 낸다.
- 닫히는 `Workspace`는 예약된 디바운스 저장을 취소한다(`saver.cancel`). 같은 시나리오를 restart로 고를 때 지운 저장을 늦게 다시 쓰지 않기 위해서다. 2단계의 즉시 저장이 그 전에 최신 상태를 이미 썼다.

## 4. 상태 모델 요약

자세한 소유권과 필드 계보는 [`01_data_contracts.md`](01_data_contracts.md).

- **원본(정본)은 최소로:** 저장되는 게임 진행 상태는 "어떤 사건에서 어떤 값을 골랐는가"의 순서 기록(`choices`)뿐이다.
- **나머지는 파생:** 현재 사건, 플래그, 해금 파일, 엔딩, Terminal 로그, 파일 표시 내용은 시나리오 + `choices`를 처음부터 재생(reduce)해 계산한다.
- 이렇게 하면 같은 사실을 두 곳에 쓰는 일이 없고, 새로고침 복원(AC-08)과 P1 되돌리기가 같은 메커니즘으로 해결된다.

## 5. 파일 내용의 3계층

ideation §4.4와 §9("기본 코드, 사용자 수정, 스토리 변경 분리")를 구조로 옮긴 것이다.

| 계층 | 소유자 | 저장 여부 |
| --- | --- | --- |
| 기본 템플릿 | 시나리오 데이터 | 저장 안 함 (번들에 포함) |
| 스토리 오버레이 (주석 변형, 사건 함수 노출, 기존 파일 변경) | Engine (Progress에서 파생) | 저장 안 함 |
| 플레이어 편집 | 플레이어 (EditorPane 경유) | 저장함 |

화면에 보이는 텍스트 = `applyEdits(render(템플릿, 오버레이), 플레이어 편집)`. `render`는 진행 상태만 반영한 `FileView`를, `applyEdits`는 거기에 편집 값을 끼운 결과를 만든다(§6.2).

- 오버레이 범위(MVP): 진행에 따라 사건 함수를 파일 아래쪽에 추가(DB-03), 새로 추가되는 함수의 주석을 플래그에 따라 선택(DB-01), 떠난 파일에 다음 파일 안내 함수 추가(§5.2). 모두 텍스트를 끼워 넣기만 하며, 이미 보인 텍스트는 바뀌지 않는다.
- 사건 함수 공개: 템플릿에는 그 스테이지의 사건 함수가 모두 들어 있고, 아직 도달하지 않은 사건의 함수 블록(바로 위 빈 줄 포함)을 `render`가 지운다. 모듈 머리(import, class 줄)와 꼬리(`if __name__ ...`)는 항상 보인다. 템플릿 안 사건 함수 순서는 `Stage.sceneIds` 순서와 같아야 한다(P04 검증).
- 함수가 추가될 때(같은 파일의 다음 사건에 도달)는 Terminal에 `[workspace] <파일>: <함수>() 추가됨` 한 줄을 남긴다. 새 스테이지 파일이 생길 때는 `[workspace] <파일> 생성됨`.
- 파일 내용이 엔진 쪽에서 바뀌었거나 처음 열린 파일을 화면에 보일 때, 현재 사건의 값 줄이 화면 밖이면 그 줄이 보이도록 스크롤만 한다(Monaco `revealLineInCenterIfOutsideViewport`). 커서는 움직이지 않고 애니메이션도 없다(R-05). P03에서는 "스크롤도 움직이지 않음"으로 정했으나, P04 실플레이에서 아래쪽에 추가된 함수가 화면 밖에 있어 찾을 수 없었으므로 바꿨다.

### 5.1 주석 변형 지시문

사건 함수 안에서만 쓰는 템플릿 전용 주석 줄이다. 화면에는 나오지 않는다.

```python
        # @if <flag> <op> <literal>
        # (조건이 참일 때 보일 주석)
        # @else
        # (아닐 때 보일 주석)
        # @end
```

- 조건은 플래그 하나에 대한 비교(`==`·`!=`·`>=`·`<=`, `Clause`와 같은 규칙)이고, 값은 리터럴 문법(§6)을 따른다. `@else`는 생략할 수 있다. 중첩은 허용하지 않는다.
- 평가 시점은 그 사건이 **현재 사건이 된 순간의 플래그**다. 나중에 플래그가 바뀌어도 이미 보인 주석은 바뀌지 않는다(DB-01).
- 잘못된 지시문(조건 형식 오류, 짝 없는 `@else`/`@end`, 닫히지 않은 `@if`, 중첩)은 `render`가 예외를 던진다. 시나리오 작성 오류이므로 P04 검증 테스트가 모든 경로를 렌더해 잡는다.
- 플레이어 편집은 지정 변수의 값 리터럴만이다(DB-02). 화면 텍스트는 매번 `render` → `applyEdits`로 재구성하므로 계층 사이 충돌이 구조적으로 없다.

### 5.2 다음 파일 안내 함수 (SoT v0.7 §3.3)

- 현재 사건이 다른 파일로 넘어가면, 떠난 파일의 **마지막으로 도달한 사건 함수 바로 아래**에 같은 들여쓰기로 `next_file()`을 넣는다. 파일 맨 끝이 아니므로 `if __name__ ...` 같은 모듈 꼬리가 있어도 클래스 안에 들어간다.
- 정본은 진행 기록이다. `derive`가 재생하면서 "떠난 파일 → 넘어간 파일"을 기록하고, `renderStage(…, handoffTo)`가 블록(`handoffBlock`)을 만든다. 문구와 경로는 엔진이 만들며 시나리오 데이터에는 없다(파생 값이므로 따로 저장하지 않음).
- 안내 함수에는 값 슬롯이 없고 실행 대상도 아니다. 넣는 위치가 모든 값 슬롯 뒤라서 기존 오프셋은 움직이지 않는다.
- 이름 `next_file`은 엔진 예약어다(`HANDOFF_FUNCTION`). 템플릿에 같은 이름의 함수가 있으면 시나리오 검증이 실패한다.
- 사건 진행은 파일 단위로도 앞으로만 간다: 전이는 같은 스테이지나 `stages` 목록에서 뒤에 있는 스테이지로만 이어져야 한다(시나리오 검증). 그래서 파일마다 안내는 많아야 하나이고, 안내가 붙은 파일에 다시 현재 사건이 생기지 않으며, 파일 순번이 진행 순서와 어긋나지 않는다.
- 편집기는 열려 있는 파일에 안내 함수가 새로 생기면, 그 파일을 보여줄 때 `def next_file(` 줄이 화면 밖이면 보이도록 스크롤만 한다(§5의 스크롤 규칙과 같은 방식).

## 6. Input Parser 규칙 (MVP)

- 입력: 필드명 → 원문 리터럴 맵. App이 `PlayerEdits`의 현재 사건 항목과, 편집하지 않은 필드의 값 슬롯 `defaultLiteral`을 합쳐 만든다(§3 2단계). 렌더된 파일 텍스트를 다시 파싱하지 않는다(DB-02(B)로 편집이 값 영역에 한정되므로 불필요).
- 리터럴 문법: 정수(`0` 외에는 0으로 시작 불가 — Python의 `01` 거부와 같다. 단 Python이 받는 `00`, 밑줄 구분자 `1_0`, 지수 표기는 지원하지 않는다), 실수, `True`/`False`, 큰따옴표·작은따옴표 문자열(앞뒤 공백 허용. 이스케이프는 `\n`·`\t`·`\\`·따옴표만 해석하고, 그 밖의 `\r`·`\0`·`\x41` 등은 백슬래시를 남긴 채 그대로 둔다 — Python 전체 이스케이프의 부분집합). 그 외(식, 함수 호출, 변수 참조, 빈 값)는 오류.
- 검증: 시나리오의 `EditableField` 정의(타입, 허용값 목록 또는 범위)와 대조.
- 오류 종류: 리터럴 아님(`not_literal`), 타입 불일치(`type_mismatch`), 허용 범위 밖(`out_of_range`). 각 오류는 Terminal에 Python 스타일 메시지로 출력한다. 타입 정의는 [데이터 계약 §4](01_data_contracts.md#4-입력-계약-parser).
- 필드 누락·중복은 구조상 발생하지 않으므로 다루지 않는다.
- 값 영역의 위치와 기본값은 Engine의 `render`가 정적 템플릿에서 계산해 **값 슬롯**으로 내보낸다([데이터 계약 §6](01_data_contracts.md#6-파생-계약-저장-안-함)). 템플릿의 사건 블록 안에서 `필드명 = 리터럴` 줄이 곧 값 영역 표식이며, 필드당 정확히 한 줄인지는 시나리오 검증 테스트가 보장한다. Editor Controller는 슬롯을 받아 그 구간만 편집을 허용하고 편집 결과를 `PlayerEdits`로 보낸다. Parser는 텍스트 위치를 모른다.

### 6.1 값 슬롯 표식 규칙

- 사건 블록은 `def 함수명(` 줄부터, def보다 깊게 들여쓴 마지막 코드 줄까지다. 빈 줄과 주석만 있는 줄(0열 주석 포함)은 블록을 끝내지 않는다.
- 사건 블록 안에서 다음 패턴에 맞는 줄이 값 슬롯이다: `^ *(필드명) *= *(리터럴) *(#.*)?$`. 들여쓰기와 구분 공백은 스페이스만 허용한다(템플릿에 탭 금지).
- 슬롯 구간(`start`~`end`)은 `(리터럴)` 부분의 문자만이다. 앞뒤 공백과 줄 끝 주석은 슬롯에 포함되지 않는다.
- 첫 번째 공백 아닌 문자가 `#`인 줄(들여쓴 주석 포함)은 `(필드명)` 자리에 `#`이 올 수 없으므로 패턴에 맞지 않는다. 따라서 선택지 설명 주석(`    # 2. action = 2 ...`)은 슬롯이 되지 않는다.
- 템플릿의 **기본값** 문자열 리터럴에는 `#`, 따옴표 이스케이프(`\`)를 쓰지 않는다. 그래야 줄 끝 주석의 시작이 모호하지 않다. 플레이어가 입력하는 값에는 이 제한이 없다(슬롯 경계는 이미 계산되어 있으므로).
- 템플릿에는 삼중 따옴표 문자열(`"""`, `'''`)을 쓰지 않는다. 설명은 모두 `#` 주석으로 쓴다.
- 사건 함수 안에 다른 `def`(중첩 함수)를 두지 않는다. 블록 경계가 들여쓰기만으로 정해지므로 중첩 함수의 줄도 슬롯 후보가 된다.
- 위 규칙은 시나리오 검증 테스트가 확인한다: 필드마다 슬롯 줄이 정확히 하나, 탭·삼중 따옴표·중첩 `def` 없음, 기본값 문자열에 `#`·`\` 없음(P04).

### 6.2 편집 반영 규칙

- 슬롯의 `start`/`end`는 `FileView.text`의 JavaScript 문자열 인덱스(UTF-16 코드 단위)다. Monaco의 `model.getPositionAt`/`getOffsetAt`이 같은 단위를 쓴다.
- 화면 텍스트는 Engine의 순수 함수 `applyEdits(fileView, edits)`가 만든다: 각 슬롯 구간을 `PlayerEdits` 값으로 바꾸고, 뒤따르는 슬롯의 오프셋을 길이 차이만큼 옮긴 새 `FileView`를 돌려준다. 슬롯 이동 규칙은 Engine의 `shiftSlots` 하나뿐이다. Editor는 수락한 변경 직후 다음 키 입력에 쓸 슬롯을 `shiftSlots`로 임시로 갱신할 뿐 이동 규칙을 따로 두지 않으며, 다음 렌더에서 `applyEdits` 결과로 덮어쓴다.
- 편집된 슬롯 자신은 `start`가 그대로이고 `end = start + 새 리터럴 길이`가 된다. 뒤따르는 슬롯은 `start`·`end` 모두 길이 차이만큼 옮긴다.
- Editor의 변경 수락 판정은 순수 함수 `acceptChange(slots, change)`로 둔다(`ui/editor/`): 변경 범위가 한 슬롯 구간 `[start, end]` 안(끝 위치 포함)이고 삽입 텍스트에 줄바꿈이 없을 때만 수락한다. 슬롯 밖 변경, 여러 슬롯에 걸친 변경, 줄바꿈 포함 변경은 거부한다(DB-02).
- 수락하면 Monaco 모델은 이미 그 변경을 담고 있으므로 다시 쓰지 않는다(커서·실행 취소 기록 유지). 슬롯의 새 텍스트를 `PlayerEdits[sceneId][field]`로 보내고, `applyEdits` 결과의 텍스트가 모델 텍스트와 같아야 한다(불변식). 어긋나면 Editor가 모델을 엔진 텍스트로 다시 써서 커서·실행 취소가 사라지므로, `applyEdits` 단위 테스트와 브라우저 확인으로 지킨다.
- 수락한 변경마다 실행 취소 단위를 닫는다(`pushStackElement`). 그래서 거부한 변경은 실행 취소 한 번으로 정확히 그 변경만 되돌릴 수 있다. 대신 실행 취소는 키 입력 하나 단위가 되고, 한글 IME 조합 중에는 조합 단계마다 단위가 생긴다(값 대부분이 숫자라 수용).
- 편집기의 자동 짝 입력(따옴표·괄호)과 자동 완성은 끈다. 짝 입력은 슬롯 밖이나 여러 범위에 걸친 편집으로 들어와 거부되면서 플레이어가 친 글자까지 지웠다(P04에서 `"backup"` 입력이 `"back"`으로 남은 문제).
- 값이 비면 밑줄 칠 글자가 없으므로, 빈 슬롯 자리에 밑줄 친 빈칸을 화면에만 끼워 넣는다(Monaco injected text, 모델 텍스트·오프셋에 영향 없음).
- 실행 단축키가 키 입력 직후(React 재렌더 전)에 눌려도 그 입력을 반영해야 하므로, App은 편집 값과 진행 기록을 상태와 함께 ref에도 즉시 기록하고 실행 시 ref를 읽는다. 재렌더 전에 두 번 실행돼도 같은 사건을 두 번 해결하지 않는다.
- 거부하면 그 변경만 되돌린다(Monaco 실행 취소 1단계).
- Editor는 엔진 쪽 텍스트(`DerivedState.files`, 편집 적용 전)와 편집 값을 따로 받는다. 모델을 다시 쓰는 것은 그 파일의 엔진 텍스트가 바뀌었거나 진행이 바뀌었을 때(사건 해결, 함수 추가, 복원 — 기본값을 `50.0`처럼 다른 표기로 써서 해결하면 엔진 텍스트는 같아도 화면은 엔진 표기로 돌아가야 한다)뿐이고(텍스트가 같아도 다시 써서 실행 취소 기록을 비운다 — 해결 직후 실행 취소로 고정된 값이 화면에서 되돌아가지 않도록. 커서·스크롤은 유지), 슬롯도 그때와 다른 파일로 바꿀 때만 엔진에서 다시 계산한다. 플레이어가 입력하는 동안 React가 넘기는 편집 값은 몇 타 늦을 수 있으므로, 그 값으로 모델이나 슬롯을 덮어쓰지 않는다(P04에서 빠른 입력 중 글자가 사라지던 문제의 원인).

## 7. 디렉터리 구조

```text
src/
  engine/          # 순수 TS: types, parser, slots, condition, render, derive(apply·derive·validPrefix)
  scenario/
    index.ts       # main.py에 나오는 시나리오 목록과 순서
    mini/          # P03 테스트·개발용 소형 시나리오 (2스테이지·엔딩 2개, 목록에는 없음)
    incident-0214/ # 첫 시나리오 데이터 + .py 템플릿 (P04)
    thermal-drift/ # 짧은 시나리오 (v0.8)
    unlogged-run/  # 짧은 시나리오 (v0.8)
  persistence/     # localStorage 어댑터(save.ts): 저장 형식, 복원 규칙, 디바운스 저장
  ui/
    explorer/  editor/  tabs/  terminal/  statusbar/
  app/             # 조립(App.tsx), 실행 한 번의 순수 함수(run.ts), Terminal 문구
    hub/           # main.py: 시나리오 목록 템플릿, 값 슬롯, runHub
```

- 시나리오 구조는 TypeScript 객체로 작성한다(DB-04). `.py` 템플릿은 TypeScript 문자열에 넣지 않고 별도 파일로 두어 Vite `?raw` import로 읽는다(들여쓰기 보존, 편집 편의).

## 8. 테스트 전략

- Engine(parser, apply, derive, 값 슬롯 계산, `applyEdits`)은 순수 함수이므로 단위 테스트의 주 대상이다. 도구는 Vite와 같이 쓰기 쉬운 Vitest를 P01에서 설정했다.
- 시나리오 검증 테스트(P04): 모든 전이 대상 존재, 모든 사건 도달 가능, 두 엔딩 각각 도달 경로 존재, 각 사건의 마지막 전이는 빈 조건, 필드마다 값 슬롯 줄이 정확히 하나, `>=`/`<=`는 숫자 값에만, 템플릿 주석의 선택지 번호와 `editableFields` 허용값 일치.
- UI는 MVP에서 수동 플레이 테스트 + 필요 시 Playwright 스모크 1~2개로 제한한다.
