# DB-02 — 편집 모델: 무엇을 편집할 수 있게 할 것인가

**상태:** Open
**관련 페이즈:** [P02](../phases/P02_core_loop_prototype.md)

## 결정이 필요한 것

ideation §2.4는 "일반 코드와 주석은 편집기에서 읽을 수 있지만, 게임 진행에 영향을 미치는 값은 미리 지정한다"고 하고, §3.1은 "기본 텍스트 편집"을, §6.1 Save Manager는 "파일 수정 내용 저장"을 요구한다. 플레이어가 지정 변수 외의 텍스트도 고칠 수 있는지가 정해져 있지 않다.

이 결정이 parser의 오류 종류, 저장 형식([데이터 계약 §5](../architecture/01_data_contracts.md#5-플레이어-편집-계약)), 스토리 오버레이와의 충돌 여부를 결정한다.

## 선택지

| 선택지 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 파일 전체 자유 편집. 실행 시 지정 변수만 해석 | 진짜 IDE와 가장 같음. Editor 구현 단순 | 플레이어가 지정 줄을 지우거나 깨뜨리면 진행 불가 상태가 될 수 있음(누락·중복 처리 필요). 파일 전체 텍스트 저장. 오버레이와 병합 규칙 필요 |
| B | 지정 변수의 **값 부분만** 편집 가능, 나머지는 읽기 전용 | 진행 불가 상태가 구조적으로 없음(AC-07). 저장은 필드 값만. 오버레이 충돌 없음. R-07(비개발자)에 유리 | "가짜 IDE" 느낌이 생길 수 있음. Monaco에 범위별 읽기 전용 기능이 없어 편집 이벤트 되돌리기 또는 데코레이션으로 직접 구현해야 함 |
| C | 전체 자유 편집 허용 + 함수 단위 "원래대로 되돌리기" 제공. 지정 줄이 깨지면 오류 메시지로 안내 | A의 자유도 유지하면서 막힘 해결 수단 제공 | A의 비용 전부 + 되돌리기 기능 추가. 게임 전용 UI 금지(R-01)와 맞는 되돌리기 형태를 따로 설계해야 함 |

## 권장안 + 이유

**B.** v0.1의 우선순위가 "코드 편집의 직관성"이고 완료 기준에 AC-07(잘못된 값이 상태를 손상시키지 않음)이 있다. B는 이 둘을 가장 싸게 보장하고, 저장·오버레이 설계도 단순해진다. 편집 불가 영역을 건드렸을 때 읽기 전용임을 보여주는 방식(커서는 들어가되 입력이 무시됨)은 실제 IDE의 읽기 전용 파일과 비슷해 R-01에도 어긋나지 않는다.

## 후속 고려 사항

- B 선택 시: 편집 가능한 값 영역의 시각 표시(옅은 밑줄 등) 여부를 P02에서 정한다.
- A/C 선택 시: 지정 줄 누락·중복 시 오류 문구, 스토리 오버레이 병합 규칙이 P02/P03 범위에 추가된다.
- P1 "조건식 수정 분기"는 편집 가능 영역을 조건식까지 넓히는 방식으로 B 위에서도 확장 가능하다.
