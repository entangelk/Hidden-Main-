# DB-04 — 시나리오 데이터 형식

**상태:** Open
**관련 페이즈:** [P03](../phases/P03_story_engine_and_save.md)

## 결정이 필요한 것

ideation §5는 스토리 데이터를 "JSON / TypeScript 객체"로 둘 다 적어 두었다. 시나리오 구조(Stage, Scene, 전이, 조건)를 어떤 형식으로 작성할지 정해야 한다. `.py` 템플릿 원문은 어느 경우든 별도 파일로 둔다([아키텍처 §7](../architecture/00_overview.md#7-디렉터리-구조-예정)).

## 선택지

| 선택지 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | JSON 파일 + 런타임 스키마 검증 | 코드와 데이터가 완전히 분리. P2 시나리오 제작 도구·외부 로딩과 바로 연결 | 타입 정의와 스키마 정의가 이중으로 생김(또는 스키마 라이브러리 의존 추가). 작성 중 오류를 실행해야 발견 |
| B | TypeScript 객체 (`satisfies Scenario`) | 작성 시점에 타입 검사·자동완성. 의존성 추가 없음. 정본 타입 하나 | 외부에서 시나리오를 불러오려면(P1/P2) 나중에 JSON 직렬화 경로를 추가해야 함 |
| C | 자체 텍스트 형식(Markdown/DSL) + 파서 | 비개발자 작성에 가장 편함 | 파서 작성·유지 비용. MVP 범위를 넘음 |

## 권장안 + 이유

**B.** MVP는 시나리오 1개를 개발자가 직접 작성하고, 정본 타입을 한 곳(`engine/types.ts`)에 두는 것이 [데이터 계약 원칙](../guides/data-contracts.md)과 맞는다. 데이터 자체는 함수·클래스 없이 순수 객체로만 쓰면 P1 "추가 시나리오 로딩" 때 JSON으로 옮기는 비용이 작다.

## 후속 고려 사항

- B 선택 시: 시나리오 파일에서 함수·클로저를 쓰지 않는다는 규칙을 P03에서 테스트 또는 lint로 확인할지 정한다.
- 시나리오 의미 검증(전이 대상 존재, 도달 가능성)은 형식과 무관하게 P04 테스트로 한다.
