# P02 — 핵심 루프 프로토타입

**상태:** Planned · [인덱스](00_index.md)

## 목표

ideation §11의 "첫 번째 프로토타입"을 만든다. **코드 편집 → 실행 → 파일 생성** 연결이 성립하는지 검증하는 것이 유일한 목적이다.

## 선행 조건

- P01 산출물: Explorer·Editor·탭·Terminal이 동작하는 IDE 셸
- [DB-02](../decision_briefs/02_editing_model.md) 해결됨: 지정 값만 편집 (B)

## 범위

- `main.py` 하나로 시작, 함수 하나에 선택지 3개(주석) + `action = 1`
- Input Parser 1차 구현 ([아키텍처 §6](../architecture/00_overview.md#6-input-parser-규칙-mvp)): 원문 리터럴 해석, 허용값 검증, 오류 메시지
- Editor 편집 제한: `acceptChange`로 값 영역 밖·여러 영역·줄바꿈 변경 거부, 값 영역 텍스트를 편집 값으로 전달 (DB-02, [아키텍처 §6.2](../architecture/00_overview.md#62-편집-반영-규칙))
- 편집 가능한 값 영역의 시각 표시(옅은 밑줄 등) 여부 결정 — R-01 범위 안에서
- `Ctrl/Cmd+Enter` → parser → 선택값별 Terminal 로그. 현재 사건의 파일(P02에서는 `main.py`, 해결 후에는 `event_002.py`)이 활성 탭이 아니면 Terminal 안내만 (SoT §3.5)
- 유효한 선택 시 Explorer에 `event_002.py` 추가 (팝업·전환 없음, R-05)
- `event_002.py` 클릭 시 다음 사건 표시
- 잘못된 값 입력 시 Terminal 오류, 상태 변화 없음 (AC-07 초기 확인)
- 탭을 닫아도 그 파일의 편집 내용은 세션 동안 메모리에 남는다(P01 동작, 다시 열면 그대로). P02에서 편집이 값 슬롯으로 바뀌면 이 동작은 `PlayerEdits`가 대신하므로, 닫은 탭의 Monaco 모델은 버려도 되는지 이때 정리한다.
- `CodeEditor`가 파일 내용 변경(엔진이 사건 함수를 추가하는 등)을 모델에 반영하도록 한다. P01에서는 모델을 처음 열 때만 만든다. 반영 시 `applyEdits` 결과와 같으면 모델을 다시 쓰지 않는다(커서·실행 취소 유지, [아키텍처 §6.2](../architecture/00_overview.md#62-편집-반영-규칙)).
- 데이터는 하드코딩 허용. 단, parser는 `engine/`에 순수 함수로 두어 P03에서 그대로 쓴다.

## 완료 기준

- 시연: `action` 값 수정 → 실행 → 로그 → 새 파일 생성 → 열기
- parser 단위 테스트: 유효 값 3종 통과, 범위 밖·리터럴 아님·타입 불일치 각 오류 반환 — 과소/과잉 엄격 양방향
- `acceptChange` 단위 테스트: 슬롯 안 변경(끝 위치 포함) 수락, 슬롯 밖·여러 슬롯·줄바꿈 변경 거부 — 양방향
- 수동: 슬롯 밖 입력이 되돌려지고 커서·실행 취소가 정상 동작
- 잘못된 값 실행 후 Terminal 오류 출력 외에는 Explorer·파일 내용·진행 상태 모두 변하지 않음을 확인
- 현재 사건 파일이 아닌 탭에서 실행하면 Terminal 안내 한 줄만 나오고 상태가 변하지 않음을 확인 (SoT §3.5)
