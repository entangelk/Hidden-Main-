# IDE 기반 선택지형 어드벤처 게임 개발 계획서

**프로젝트명:** Incident Workspace (가칭)  
**버전:** 기획안 v0.1  
**개발 형태:** 개인 사이드 프로젝트 / 웹 애플리케이션  
**예상 개발 기간:** 4주 (주 8~12시간 작업 가정)  
**목표:** 실제 코드 편집기처럼 보이는 환경에서 진행되는 스토리 중심 어드벤처 게임

---

## 1. 프로젝트 개요

### 1.1 기획 의도

일반적인 게임 인터페이스를 사용하지 않고, 소스코드 편집기(IDE)의 파일 탐색기, 코드, 주석, 변수, 조건문 및 실행 로그를 게임의 인터페이스로 활용한다.

사용자는 소스코드를 읽고 수정하면서 이야기의 방향을 결정한다. 특정 조건을 만족하면 프로젝트에 새로운 파일이 생성되고, 해당 파일을 열어 다음 스테이지를 진행한다.

**핵심 콘셉트:**

> 남이 보기에는 프로그래밍 작업이지만, 사용자에게는 코드 안에서 진행되는 선택지형 어드벤처 게임.

### 1.2 설계 원칙

1. 별도의 게임 화면을 만들지 않는다.
2. 게임의 이야기는 코드 주석을 통해 전달한다.
3. 사용자의 선택은 변수 값이나 조건식을 수정하는 방식으로 이루어진다.
4. 함수는 하나의 사건 또는 선택 상황을 나타낸다.
5. 파일은 하나의 스테이지를 나타낸다.
6. 폴더는 챕터 또는 이야기의 영역을 나타낸다.
7. 다음 스테이지에 도달하면 Explorer에 새로운 파일이 생성된다.
8. 게임 실행 결과는 터미널 로그 또는 코드의 변경으로 표현한다.
9. 플레이어가 실제 프로그래밍 언어를 몰라도 진행할 수 있어야 한다.

## 2. 핵심 게임 플레이

### 2.1 기본 진행 구조

**프로젝트 열기 → 코드 주석 읽기 → 변수 수정 → 코드 실행 → 결과 확인 → 새로운 함수 또는 파일 해금**

사용자는 처음에 일반적인 개발 프로젝트처럼 보이는 화면을 접한다.

- 왼쪽에는 Explorer가 표시된다.
- 중앙에는 Python 형식의 코드가 표시된다.
- 하단에는 실행 결과를 보여주는 Terminal이 존재한다.
- 상단에는 열린 파일의 탭이 표시된다.

초기 프로젝트에는 최소한의 파일만 표시된다.

### 2.2 선택지 시스템

하나의 함수에 다음 요소를 포함한다.

- 함수 이름: 현재 사건을 식별하는 역할
- 상단 주석: 현재 상황과 선택지 설명
- 더미 코드: 실제 프로그램처럼 보이기 위한 처리 로직
- 수정 가능한 변수: 플레이어의 선택 입력
- 조건문: 선택에 따른 분기 표현

예시:

```python
class AccessController:

    def validate_entry(self):
        # 출입 시스템에 비정상적인 접근 기록 감지.
        # 1. 접근 기록을 분석한다.
        # 2. 잠금 장치를 해제한다.
        # 3. 해당 요청을 무시한다.

        request_id = 2048
        confidence = 0.73
        threshold = 0.65

        action = 1

        if confidence >= threshold:
            return self.process(action)

        return self.reject(request_id)
```

사용자는 `action = 1`의 숫자를 수정하고 `Ctrl+Enter`로 실행한다.

게임 엔진은 수정된 값을 읽어 해당 분기의 결과를 처리한다.

### 2.3 스테이지 이동

하나의 파일 내부에서는 여러 함수가 순차적으로 열릴 수 있다.

해당 스테이지의 완료 조건을 만족하면:

1. 현재 함수의 실행이 완료된다.
2. 게임 엔진이 다음 스테이지의 잠금 상태를 해제한다.
3. Explorer에 새로운 Python 파일이 추가된다.
4. 플레이어가 해당 파일을 열면 다음 스테이지가 시작된다.

새 파일 생성 시 전체 화면 전환이나 게임 전용 팝업을 사용하지 않는다.

**파일 생성 자체가 스테이지 해금 연출이다.**

### 2.4 코드 수정 범위

초기 버전에서는 모든 Python 문법을 자유롭게 해석하지 않는다.

게임 엔진이 인식하는 수정 항목을 제한한다.

| 입력 유형 | 예시 | 역할 |
|---|---|---|
| 정수 | `action = 2` | 기본 선택지 |
| 불리언 | `override = True` | 특별 행동 |
| 수치 | `limit = 50` | 특정 조건 변경 |
| 문자열 | `target = "A"` | 대상 선택 |

일반 코드와 주석은 편집기에서 읽을 수 있지만, 게임 진행에 영향을 미치는 값은 미리 지정한다.

향후 확장 단계에서 조건문 수정과 복합 변수 조작을 지원한다.

## 3. 게임 화면 설계

### 3.1 화면 구성

**A. Explorer (왼쪽)**

- 프로젝트 폴더 트리 표시
- 해금된 파일 표시
- 파일 클릭으로 스테이지 이동
- 새 파일 생성 상태 반영
- 챕터 진행에 따른 하위 폴더 추가
- 이전에 접근했던 파일 재열람 지원

**B. Code Editor (중앙)**

- Python 문법 강조
- 줄 번호 및 들여쓰기
- 기본 텍스트 편집
- 변수 값 변경
- 기존 함수 접기 및 펼치기
- 열린 파일 탭 관리
- 수정된 파일 상태 표시

**C. Terminal (하단)**

- `Ctrl+Enter` 실행 결과 표시
- 선택 처리 및 사건 결과 로그 출력
- 잘못된 입력에 대한 오류 출력
- 새로운 파일 생성에 대한 로그 출력

**D. Status Bar (하단)**

- Python 언어 표시
- 파일 인코딩 표시
- 현재 파일 및 프로젝트 상태 표시

### 3.2 시각적 디자인

전체 화면은 VS Code를 연상시키는 다크 테마로 구성한다.

일반적인 개발 작업처럼 보이도록 다음 요소는 사용하지 않는다.

- 게임 전용 메인 메뉴
- 체력 바, 점수, 경험치
- 커다란 선택지 버튼
- 스테이지 클리어 팝업
- 화려한 전환 애니메이션
- 게임 전용 효과음

첫 MVP에서는 VS Code의 모든 기능을 복제하지 않고, 게임 진행에 필요한 최소한의 외형과 조작만 구현한다.

## 4. 스토리 시스템 설계

### 4.1 기본 스토리

**가제: Incident 02:14**

플레이어는 비정상적인 시스템 장애를 조사하는 개발자다.

처음에는 단순한 서버 오류처럼 보이지만, 로그와 설정 파일을 확인할수록 설명되지 않는 사건이 발견된다.

플레이어의 선택에 따라 조사 경로와 사건의 결말이 달라진다.

### 4.2 MVP 스테이지 구성

| 스테이지 | 생성되는 파일 | 주요 사건 |
|---|---|---|
| 01 | `event_001.py` | 최초 장애 발생 |
| 02 | `security_audit.py` | 비정상 접속 기록 발견 |
| 03 | `power_control.py` | 전력 계통 이상 확인 |
| 04 | `sublevel_access.py` | 제한 구역 접근 |
| 05 | `case_report.py` | 사건 최종 처리 |

각 파일에는 2~3개의 주요 사건 함수를 배치한다.

최초에는 `main.py`, 설정 파일, 첫 사건 파일 정도만 표시하고, 진행에 따라 새 파일을 추가한다.

### 4.3 분기 시스템

선택 결과는 이후 장면에 영향을 준다.

예시:

- 보안 기록을 확인했다면 이후 장면에 추가 단서 제공
- 위험한 명령을 실행했다면 시스템 경고 발생
- 접근 권한을 수정했다면 숨겨진 함수 또는 파일 해금
- 이전 선택에 따라 동일한 함수의 주석 내용 변경

결과는 게임의 상태값으로 저장한다.

MVP에서는 **일반 엔딩 2개**를 구현하고, 히든 엔딩은 후속 버전으로 분리한다.

### 4.4 이전 파일과의 상호작용

한 번 생성된 파일은 기본적으로 유지된다.

이후 선택에 따라 기존 파일의 내용이 업데이트될 수 있다.

예를 들어 이전에 잠근 문이 나중에 열린 상태로 변경되고, 해당 파일에 경고 주석이 추가되는 방식이다.

파일 변경은 스토리 엔진이 관리하며, 플레이어가 직접 수정한 입력값과 충돌하지 않도록 별도의 상태로 보관한다.

## 5. 기술 스택

| 구분 | 선택 기술 | 목적 |
|---|---|---|
| 프론트엔드 | React + TypeScript | 화면 및 게임 상태 관리 |
| 빌드 도구 | Vite | 개발 환경 및 빌드 |
| 코드 편집기 | Monaco Editor | IDE 스타일 편집 기능 |
| 스타일 | CSS | Explorer, Terminal, 탭 구현 |
| 게임 엔진 | TypeScript | 선택지 해석 및 스토리 진행 |
| 스토리 데이터 | JSON / TypeScript 객체 | 장면과 분기 관리 |
| 저장 | localStorage | 자동 저장 및 이어하기 |
| 배포 | 정적 웹 호스팅 | 브라우저에서 실행 |

초기에는 백엔드와 데이터베이스를 사용하지 않는다.

모든 게임 로직은 브라우저에서 처리한다.

### 5.1 실제 Python 실행 여부

**MVP에서는 Python 코드를 실제로 실행하지 않는다.**

화면에는 Python 코드가 표시되지만, 내부 게임 엔진이 지정된 변수와 조건만 해석한다.

이 방식은 다음 장점이 있다.

- 서버가 필요하지 않다.
- 임의 코드 실행에 따른 보안 위험을 줄인다.
- 플레이어의 입력 범위를 통제할 수 있다.
- 스토리 분기 테스트가 쉽다.
- 브라우저에서 빠르게 실행할 수 있다.

추후 필요하면 더 정교한 Python 구문 분석을 도입할 수 있다.

## 6. 게임 엔진 아키텍처

### 6.1 주요 모듈

**Workspace Manager**

- Explorer 파일 트리 관리
- 파일 생성 및 잠금 해제
- 현재 열린 파일 관리
- 동적 파일 내용 업데이트

**Editor Controller**

- Monaco Editor 연결
- 변경된 코드 내용 관리
- 수정 가능한 변수 추적
- 키보드 단축키 처리

**Input Parser**

- 편집된 코드에서 지정 변수 추출
- 정수, 문자열, 불리언 값 검사
- 입력 유효성 검증
- 변경된 값과 게임 액션 연결

**Story Engine**

- 현재 스테이지 및 사건 관리
- 선택 조건 평가
- 스토리 상태값 변경
- 다음 장면 및 스테이지 결정
- 엔딩 분기 처리

**Save Manager**

- 진행 상태 저장
- 파일 수정 내용 저장
- 잠금 해제된 파일 목록 저장
- 브라우저 재접속 시 복구

**Terminal Renderer**

- 실행 로그 출력
- 오류 및 경고 메시지 출력
- 다음 파일 생성 메시지 출력

### 6.2 스토리 데이터 구조

각 스테이지와 사건은 코드에서 분리된 데이터로 관리한다.

**Stage**

- `id`: 스테이지 식별자
- `filePath`: 생성할 파일 위치
- `initialCode`: 기본 소스코드
- `scenes`: 포함된 사건 목록
- `unlockCondition`: 잠금 해제 조건

**Scene**

- `id`: 사건 식별자
- `functionName`: 코드상 함수 이름
- `description`: 주석으로 표시할 이야기
- `editableFields`: 수정 가능한 변수 목록
- `transitions`: 선택별 다음 사건
- `effects`: 선택 결과로 변경되는 상태

**GameState**

- 현재 파일
- 현재 함수
- 해금된 파일 목록
- 사건 진행 기록
- 스토리 플래그
- 사용자 코드 수정 내용
- 엔딩 상태

스토리 내용과 게임 엔진을 분리해, 새로운 시나리오를 만들 때 엔진을 수정하지 않도록 설계한다.

### 6.3 실행 처리 흐름

1. 사용자가 코드를 수정한다.
2. `Ctrl+Enter`를 입력한다.
3. Editor Controller가 현재 코드 내용을 읽는다.
4. Input Parser가 유효한 선택값을 추출한다.
5. Story Engine이 선택 결과와 상태 변화를 계산한다.
6. 결과를 Terminal에 기록한다.
7. 다음 함수 또는 파일을 해금한다.
8. 변경된 상태를 저장한다.

입력한 코드 전체를 `eval`하거나 직접 실행하지 않는다.

## 8. 개발 일정

### Week 1 — IDE 인터페이스 구현

**목표:** 실제 코드 편집 환경처럼 작동하는 기본 화면 완성

작업:

- React 프로젝트 초기화
- Monaco Editor 연결
- 다크 테마 구성
- Explorer 구현
- 파일 탭 구현
- Terminal UI 구현
- 기본 Python 파일 표시

**결과물:** 코드를 열람하고 수정할 수 있는 가짜 IDE

### Week 2 — 게임 엔진 구현

**목표:** 코드의 변수 수정으로 사건을 진행할 수 있는 상태

작업:

- 스토리 데이터 포맷 정의
- 게임 상태 관리
- 입력값 추출 및 검증
- 선택지 분기 처리
- `Ctrl+Enter` 실행 연결
- Terminal 로그 연결
- 파일 생성 및 해금 처리
- 자동 저장 구현

**결과물:** 선택에 따라 새로운 파일이 생성되는 최소 동작 프로토타입

### Week 3 — 첫 번째 스토리 제작

**목표:** 처음부터 엔딩까지 플레이 가능한 시나리오 완성

작업:

- 스테이지 5개 작성
- 사건 함수 약 10~15개 작성
- 스토리 분기 연결
- 엔딩 2개 구현
- 선택에 따른 로그 변화
- 잘못된 입력 처리
- 이전 파일 상태 유지
- 분기별 테스트

**결과물:** 완결된 짧은 미스터리 어드벤처

### Week 4 — 완성도 개선 및 배포

**목표:** 실제 브라우저에서 안정적으로 즐길 수 있는 MVP

작업:

- 주요 버그 수정
- Editor 입력 및 단축키 개선
- 파일 생성 동작 다듬기
- 코드와 주석의 가독성 개선
- 파일 저장 및 복구 테스트
- 배포용 빌드
- 정적 웹 호스팅 배포
- 사용자 플레이 테스트

**결과물:** 외부 사용자에게 공유 가능한 MVP v0.1

## 9. 주요 개발 위험 및 해결 방안

| 위험 | 대응 방안 |
|---|---|
| 자유로운 코드 수정으로 분기가 깨지는 문제 | MVP에서는 허용된 변수만 해석 |
| 게임 진행 방법을 알아보기 어려움 | 짧고 명확한 주석과 숫자 선택지 제공 |
| 더미 코드가 지나치게 부자연스러움 | 사건과 관련된 일관된 업무용 코드 사용 |
| 분기가 많아져 관리가 어려워짐 | 데이터 기반 상태 머신과 공통 합류 지점 활용 |
| 기존 파일과 새 파일의 상태 충돌 | 기본 코드, 사용자 수정, 스토리 변경 분리 |
| 새로고침 시 진행 정보 소실 | 변경 시 자동 저장 및 상태 복원 |
| 콘텐츠 제작 시간이 지나치게 증가 | 5개 스테이지, 2개 엔딩으로 MVP 제한 |

## 10. MVP 완료 기준

다음 조건을 모두 만족하면 v0.1을 완료한 것으로 판단한다.

1. 게임 화면 없이 IDE 인터페이스만으로 처음부터 끝까지 플레이할 수 있다.
2. 사용자가 코드의 숫자나 변수를 수정해 선택할 수 있다.
3. 실행 결과에 따라 이야기와 상태가 변화한다.
4. 스테이지 해금 시 Explorer에 새로운 파일이 나타난다.
5. 생성된 파일을 열면 다음 스테이지가 진행된다.
6. 사용자가 이전 파일을 열어 내용을 다시 확인할 수 있다.
7. 잘못된 값을 입력해도 진행 상태가 손상되지 않는다.
8. 브라우저를 새로고침해도 진행 상태가 유지된다.
9. 선택에 따라 최소 2개의 결말에 도달할 수 있다.
10. 일반적인 플레이 기준 약 10~20분 분량의 시나리오를 제공한다.

## 11. 권장 개발 순서

전체 계획 중 가장 먼저 검증해야 할 것은 스토리의 재미보다 **코드 편집 → 실행 → 파일 생성**의 연결이다.

이를 위해 다음의 최소 기능을 가장 먼저 만든다.

**첫 번째 프로토타입**

- `main.py` 파일 하나로 시작
- 함수 하나에 선택지 3개 표시
- 사용자가 `action` 값을 수정
- `Ctrl+Enter`로 값 검증
- 선택한 값에 따라 Terminal 로그 출력
- Explorer에 `event_002.py` 생성
- 새 파일 클릭 시 다음 사건 표시

이 일련의 동작이 완성되면 핵심 기술 검증이 끝난다.

이후 스토리 시스템, 상태 저장, 분기 기능을 단계적으로 추가한다.

## 12. 최종 방향

이 프로젝트의 경쟁력은 복잡한 게임 시스템이나 실제 프로그래밍 실행 환경이 아니다.

**IDE라는 익숙한 개발 도구의 인터페이스를 게임의 규칙과 세계로 재해석하는 경험**이다.

따라서 개발 우선순위는 다음과 같다.

**코드 편집의 직관성 → 파일 생성 경험 → 이야기의 몰입감 → 복잡한 코드 조작**

첫 버전에서는 이 순서를 유지하며, 제한된 개발 범위 안에서 완성도 높은 플레이 경험을 만드는 것을 목표로 한다.
